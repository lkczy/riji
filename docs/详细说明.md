[`README.md`](../README.md) 是给第一次看到这个项目的人看的：主要功能和怎么开始用。
**这一份是它的详细版**——每一项功能到底怎么用、以及为什么这么设计（包括哪些地方是刻意的取舍、
哪些是已知的坑）。想改这个项目的话，先看 [`开发须知.md`](开发须知.md)。

- 数据格式规范见 [`docs/DATA-FORMAT.md`](DATA-FORMAT.md) —— 那是全项目唯一不可逆的部分，优先于一切实现细节。

- 备份：关程序时自动做一次（**一天至多一份**，自动快照只保留最近 30 份；手动快照永不删除）。备份位置要你自己设——**和日记在同一个盘时挡不住盘坏**，界面会如实告诉你这一点。
- 当前状态：Windows 桌面版可用，666 个测试覆盖。手机端**未开始**（`docs/手机写作.md` 里有一条零开发的替代路线，已实测可用）。

## 怎么启动

**双击项目根目录里的 `riji.lnk` 即可**（或者用 `riji.bat`，两者等效）。

### 为什么不是一个单独的 exe

Flutter 的 Windows 程序**不是一个文件，而是一个文件夹**：

```
build\windows\x64\runner\Release\
├── riji.exe          88 KB    ← 只是个外壳，单独挪走打不开
├── flutter_windows.dll   20 MB    ← 渲染引擎，必须同目录
└── data\                 7 MB     ← 编译后的 Dart 代码 + 资源，必须同目录
```

所以**不能把 exe 单独拷到浅一点的地方**。要在浅位置双击启动，只有两条路：

| 做法 | 说明 |
|---|---|
| **启动器**（当前用的） | 根目录放 `riji.lnk` / `riji.bat` 指向真正的 exe。不复制文件，永远启动最新构建 |
| **复制整个文件夹** | 把上面 4 项一起拷到别处（如 `D:\Apps\riji\`）。占额外 29MB，且每次重新构建后都要再拷一次 |

`riji.lnk` 由 `tool\build_release.ps1` 在每次构建后自动重新生成，所以不会指向旧位置。
`riji.bat` 是纯文本、用相对路径（`%~dp0`），跟着项目文件夹搬到哪都能用。

## 写入保护：绝不静默覆盖

这是这个程序里最要紧的一条行为。触发场景都是「本地优先 + 多端同步」必然出现的：

- Syncthing 从手机同步过来一段话，你同时在电脑上继续编辑
- 程序开了两个窗口，一个窗口的改动被另一个抹掉
- 你用 VS Code / 记事本改了当天的 `.md`，程序没有重新读

**做法**：存储层记住「每个文件我上次读到的原始内容」。保存前重新读一次磁盘，
如果发现内容已经变了，就**两个版本都保留**：

| 版本 | 去向 |
|---|---|
| 对方的（磁盘上现有的） | 原样另存为 `YYYY-MM-DD.conflict-<时间>-<设备>.md` |
| 你的（正在编辑的） | 正常写入正式文件 |

然后在界面顶部顶出一条**不会自动消失**的警告条，告诉你冲突文件在哪、去合并。

不做的事：不自动合并（程序无法判断你想留哪句话）、不覆盖对方、不把提示做成
几秒后消失的 toast（那等于把冲突埋起来，和静默覆盖只差一步）。

### 单实例锁

上面第二条（「程序开了两个窗口」）其实**不该发生**，所以现在直接堵住：

| 做法 | 为什么不用另一个做法 |
|---|---|
| 用一个**操作系统级的文件锁**（`FileLock.exclusive`）锁住 `%APPDATA%\riji\instance.lock` | 自己维护一个带 PID 的锁文件，就得判断「那个进程还活着吗」。这个判断本身会出错（PID 会被复用），最后表现成「程序说你已经开了一个，其实没有」，而用户只能手工去删文件 |
| 锁文件放**设置目录**，不放日记目录 | 单实例是「每台机器」的概念，而日记目录是可配置、会被同步到别的设备的 |
| 拿不到锁就显示一个说明页，不启动日记界面 | 第二个实例仍然会开一个窗口（不用插件没法把已开那个窗口调到前台），但它**完全不碰日记目录**——一行设置都不读 |

进程崩溃、被任务管理器杀掉、断电时，操作系统会自动释放这个锁，不会留下
需要手工清理的残留。跨进程验证过：程序运行时，另一个进程尝试加锁会失败。

## 每日一问与时光机

### 每日一问

**还没动笔时**（正文、心情、天气、标签全空）在编辑区上方给一个写作引子，
一开始写就自动消失——空页面才是障碍，有内容之后就不是了。

120 条引子，**12 个角度**各 10 条：今天发生了什么 / 感受 / 人 / 观察与细节 /
身体 / 思考与反思 / 工作与学习 / 感恩与小确幸 / 想象与假设 / 未来与计划 /
换位与对话 / 随想与碎片。多角度是有意的——同一个问题再深刻，天天问也会失效，
换一个角度往往才能让人想起今天真正值得记的那件事。

三条刻意保证的性质（都有测试守着）：

| 性质 | 为什么 |
|---|---|
| **同一天永远是同一条** | 做成随机的话，切走再回来就换成别的了，用户会怀疑自己记错 |
| **相邻日期一定在不同角度上** | 否则会连着十天都在问同一类问题，一样没话说 |
| **任意连续 120 天刚好覆盖全部 120 条** | 靠「步长与总数互质」这条数论性质，不重不漏 |

「换一个」改变的是相位而非步长，相位步长同样与总数互质，
所以换满一圈刚好遍历全部引子，不会反复撞同几条。

**引子不写进日记文件**：它是写作的脚手架，不是日记的内容。
（想要的话可以自己把问题抄进正文。）

### 时光机

编辑区右上角的骰子图标。随机翻到一篇以前写过的日记，跳完给一条可
「再翻一篇」的提示。

只挑**正文非空**的条目——翻到空白的一天毫无意义，反而让人以为日记丢了。
也不会连续翻到同一条（否则观感像"点了一下没反应"）。

## 字体与格式

这两件事经常被混在一起，但它们完全不同，风险也完全不同。

### 编辑器排版（字号 / 行距 / 字重 / 行宽）

入口：标题栏的**「外观」菜单 → 字体与行距**（和主题放在一起，因为都是"看着舒服"这一类）。

改动**即时生效、随改随存**，没有「应用/取消」——这类"看着调"的设置，反馈回路越短越好。
想退回去点「恢复默认」。

| 项 | 范围 | 默认 |
|---|---|---|
| 字号 | 13–28 px | 16 |
| 行距 | 1.3–2.8 倍 | 1.9 |
| 字重 | 常规 / 中等 / 加粗 | 常规 |
| 行宽 | 520–1100 px | 760 |

**这些设置永远不写进日记文件。** 正文是纯文本，换台机器、换个程序打开，内容一模一样；
排版是各人看着舒服就好的事，不该跟着文件跑，也不该在同步时互相覆盖。
设置读进来时每个值都会**夹回合法范围**——设置文件被改坏不该让正文变成 0 号字。

### 内联格式（加粗 / 斜体 / 下划线）

编辑区上方有一排格式按钮，也支持快捷键：

| 操作 | 快捷键 | 写进文件的样子 |
|---|---|---|
| 加粗 | `Ctrl+B` | `**文字**` |
| 斜体 | `Ctrl+I` | `*文字*` |
| 下划线 | `Ctrl+U` | `<u>文字</u>` |

**这里做的是插入 Markdown 标记，不是改某个加粗属性。** 原因：富文本意味着正文要存成
带格式的数据结构，而 Markdown 源码本身就是最好的格式——几十年后还能读、能 grep、
能 diff、能用任何编辑器打开。代价是源码里能看到标记符号，换来的是文件永远是纯文本。

几个刻意的行为：

- **再按一次取消格式**（标记在选区里、或紧贴选区两侧，两种都能识别）
- **斜体不会把粗体拆坏**：在 `**粗体**` 里选中文字按斜体，会再包一层变成 `***文字***`，
  而不是拆出一个残缺的 `*文字*`
- **光标没选中东西时**，插入一对空标记并把光标放在**两个标记之间**（不是选中整对标记，
  否则一打字就把标记全替掉了，格式反而没了）

**关于下划线**：Markdown 没有原生的下划线语法（`_` 是斜体的另一种写法）。
这里用 `<u></u>` 内联 HTML，是 CommonMark 允许的写法，但**不是所有 Markdown 渲染器都认**，
而且在源码里比 `**` 更显眼。如果只是想做强调，建议用粗体代替。

## 农历、节日与节气

左侧日期列表的每一行，按下面的位置显示这一天的时间信息：

```
2026-10-01 周四 国庆节              平静     阳历节日在日期后面
八月廿一                                     普通日子只有农历
把日记程序的数据格式定下来了。

2026-02-17 周二                    平静
春节 · 正月初一                              阴历节日在农历日期前面
过年了。

2026-02-18 周三                    平静
正月初二 · 雨水                              节气在农历日期后面
雨水的节气到了。

2027-08-08 周日                    平静
七夕 · 七月初七 · 立秋                       第二行三段齐全时的顺序
2031-10-01 周三 国庆节             平静
中秋节 · 八月十五                            同一天既是阳历节日又是阴历节日
```

| 内容 | 位置 |
|---|---|
| 阳历节日 | 跟在**阳历日期**后面（第一行） |
| 阴历节日 | 排在**农历日期**前面（第二行） |
| 二十四节气 | 排在**农历日期**后面（第二行） |

阳历节日和阴历节日在数据层就是**两个独立字段**，因为在界面上它们要出现在两个不同位置。
两者可能撞在同一天——1950–2100 这 151 年里就有 **45 天**是这样，比如
**2031-10-01 是国庆节 + 中秋节**、1982-10-01 也是，2033-02-14 是情人节 + 元宵节。
所以不能合并成一个字段，否则会丢掉一个。有测试扫过全部 151 年找出这种重合的日子，
确认两边都保留、且分别落在两行上。

颜色也有区分：节日用主色加粗（最显眼），农历日期最淡，节气用第三个颜色和节日分开。
第二行用 `Text.rich` 拼成一行，窄侧栏下整体省略号收尾，不会溢出。

包含的内容：

| 类别 | 举例 |
|---|---|
| 农历日期 | `正月初一`、`闰六月十三`、`腊月廿七` |
| 公历节日 | 元旦、情人节、妇女节、劳动节、儿童节、国庆节、圣诞夜…… |
| 按星期算的 | 母亲节（5 月第二个星期日）、父亲节、感恩节 |
| 农历节日 | 春节、元宵节、端午节、七夕、中秋节、重阳节、腊八节、除夕 |
| 二十四节气 | 立春、清明、夏至、霜降、冬至…… |

**除夕不是写死的「腊月三十」**：腊月有时 29 天有时 30 天，所以是按
「第二天是正月初一」判定的。闰月里的同名日子也不算农历节日
（闰五月初五不是端午）——这条有测试扫过全部 151 年。

### 为什么是查表而不是推算

农历要算朔望月，节气要算太阳黄经，两者都是**天文推算**。用低精度公式在个别年份
会差一天，而日记里显示错日期比不显示更糟。所以数据是生成的，并且经过交叉验证：

| 项目 | 结果 |
|---|---|
| 数据范围 | 公历 1950–2100（表里多存 1949 和 2101 两个农历年，用来夹边界） |
| 交叉验证 | 和 .NET 的 `ChineseLunisolarCalendar` **逐日对拍 55544 天** |
| 一致 | 只有 60 天不一致，集中在 2089 和 2097 各一处月首边界 |
| 那 60 天的裁决 | 另有三个独立实现（lunar_python / cnlunar / zhdate）与 .NET 意见相反，**3 比 1**，所以采用了多数派 |

范围外一律返回 `null`，界面就是空的——**宁可什么都不显示，也不显示错的**。

复现验证：

```powershell
# 生成数据表（需要 pip install lunar_python）
python tool\generate_chinese_calendar.py --emit-dart lib\core\chinese_calendar_data.dart --emit-fixture test\chinese_calendar_fixture.dart

# 和 .NET 逐日对拍
powershell -File tool\verify_lunar_against_dotnet.ps1
```

解码这部分（拆位段、从正月初一往前走）由 `test/chinese_calendar_fixture.dart` 里的
357 个边界日期守着：每个农历年的正月初一、每个闰月的初一、每一年的除夕。

## 右下角的「更多」菜单

编辑区右下角（也就是窗口右下角）有一个 `⋮` 按钮，日记的"非写作"操作都收在这里：

| 菜单项 | 做什么 |
|---|---|
| 打开日记文件夹 | 在资源管理器里定位到日记目录 |
| 日记存储位置 | 改日记存哪（见下面的「更改日记位置」） |
| 导出 | 导出成单个 Markdown 文件 |
| 备份 | 立刻做一份备份（见下面的「备份」）。预览模式下这一项整个不出现 |
| 历史版本 | 查看 / 恢复历史快照 |
| 回收站 | 查看 / 恢复 / 永久删除已删除的日记 |
| 删除这一天的日记 | 软删除当前这一天；这一天还没写过时置灰 |

顺序是刻意的：**日常操作在上，数据管理在中，破坏性的单独隔在下**。删除项在
没写过东西时是**置灰而不是隐藏**——隐藏会让人以为没这个功能。

> **关于「…」**：菜单项后面**不带**「…」，而对话框内部的按钮（比如
> 「设置备份位置…」「从备份恢复…」）**保留**它。理由：这个菜单里每一项都会
> 打开对话框或确认框，有的带有的不带反而不一致，所以菜单统一去掉；
> 而对话框里的按钮确实会再弹一层，留着更准确。

> 收进菜单之前，「打开文件夹」和「导出」是常驻在状态栏上的两个按钮。
> 顺带修掉了一个真实的布局问题：状态栏当时用「`Spacer` + `Flexible`」分配空间，
> 两者各占一半自由空间，而 `Flexible` 是松约束——路径文字用不到那一半时，
> 多出来的空白**不会还回去**，于是 `⋮` 被留在了偏中间的位置
> （实测：窗口宽 1200，按钮中心停在 928 而不是贴到右边缘）。
> 现在路径改用 `Expanded` 吃掉剩余空间并右对齐，按钮才真正落在角上。
> 界面测试用**坐标**验证这一点，而不是只验证按钮存在。

## 命令面板（Ctrl+K）

**功能越加越多，功能就越找不到。** 这个项目里"功能藏得太深"已经反复出现过，所以
把界面上**每一个**动作做成一张可搜索的表：

```
Ctrl+K（或状态栏那个放大镜）
输入「深色」→ Enter        切到深色
输入「行距」→ Enter        打开字体与行距
输入「删除」→ Enter        删除这一天（仍然要确认）
```

`↑↓` 选、`Enter` 执行、`Esc` 关掉，鼠标点也行。

### 它不是新功能，是已有功能的第二道门

菜单、按钮、快捷键**一个都没动**。新手继续靠看得见的东西，熟练的人靠搜——两个都要
（格式条那边已经写过同一条道理：「有了按钮，快捷键才被发现；有了快捷键，写起来才
不用离开键盘」）。

所以面板里能搜到的，界面上都找得到；反过来说，**改功能时这两处要一起改**，
别让它们分叉。

### 行尾显示快捷键，于是「快捷键总览」不用再单独做

这是顺手拿到的：面板每一行的右边就是它的快捷键（`Ctrl+B` / `Ctrl+I` / `Ctrl+U`）。
这一份的「下一步」里那条「快捷键总览」到这里就算交付了。

### 三条让它真正好用的东西

| 东西 | 为什么 |
|---|---|
| **别名** | 中文没有词边界，只按标题匹配的话用户十有八九搜不到。想切深色的人会打「主题」「夜间」「暗」，不会去打「外观：深色」。所以每条命令都带几个"用户会想到的另一个说法" |
| **排序** | 子序列匹配（打「字行」也能命中「字体与行距」），但**连续命中显著高于跳着命中**、**标题命中显著高于别名命中**。搜「深色」时「外观：深色」必须在第一条 |
| **禁用而不是隐藏** | 不能用的命令照样出现在列表里，并把原因写在它自己那一行上（「删除这一天的日记」下面是「这一天还没写东西」）。隐藏会让用户以为程序没这个功能——这条原则和「更多」菜单一致 |

排序规则是**纯逻辑**（[`lib/core/command_palette.dart`](../lib/core/command_palette.dart)），
所以它能被一条条量出来：搜「夜间」得到哪几条、谁排第一、多词是不是「与」关系，
都有测试守着。

### 它不做的事

- **不搜正文**。搜内容是左侧那个搜索框的活。面板搜的是"动作"，
  两者混在一起会让两边都变模糊。
- **不做命令历史落盘**，也不支持自定义键位。
- **不支持拼音缩写**（打 `zt` 找「主题」）。要做就得引入一张拼音表，
  换来的便利和它的维护成本不成比例。

### 已知的限制（如实记）

- **只按 Ctrl+K 就能开的窗口，在浏览器预览里会被吃掉**：`flutter run -d chrome`
  下 Flutter 的文本框占用了 `Ctrl+K`（Emacs 式的 kill line，只在 macOS 和 web 生效）。
  那是预览环境，不是目标形态；桌面版实测正常。
- **中文输入法组合态下 Ctrl+K 会不会被输入法吃掉，没有在真机上验过**——
  见 [`docs/开发须知.md`](开发须知.md) 的「验证状态」。

### 动作实现只有一份

面板挂在 `HomePage` 上（必须在**侧栏搜索框有焦点时**也能唤出，而侧栏和写作区是
兄弟，挂在写作区里面就够不到它）。但"打开文件夹""导出""删除""时光机""加粗"
这些动作的实现原本是 `EditorPanel` 的私有方法——两边各留一份迟早会分叉，
所以实现统一搬到了 [`lib/ui/diary_actions.dart`](../lib/ui/diary_actions.dart)：
「更多」菜单和命令面板调的是同一个函数。

## 本版更新

**升级之后第一次启动**弹一个小窗，只讲四件事：

```
本版更新
日迹 1.2.0    2026-10-04 发布

新功能
· 命令面板：按 Ctrl+K 唤起，打几个字就能搜到界面上每一个动作
· …
修复
· …
```

没有第五件事。内部改动、已知限制、设计取舍全部留在
[`CHANGELOG.md`](../CHANGELOG.md) 里——把整份更新记录摊在启动时，用户只会学会无脑点掉。

### 内容就是 CHANGELOG，没有第二份要维护

弹窗里的文字**直接从 [`CHANGELOG.md`](../CHANGELOG.md) 读**，所以：

- 写 changelog 就是在写弹窗文案，不存在"两处对不上"的可能
- 哪些内容进弹窗由文件格式决定：只有 **`### 新功能`** 和 **`### 修复`** 两节会进去，
  其余小节不会。约定写在那个文件开头
- 行内标记（`**加粗**`、`` `反引号` ``、链接）在读的时候就剥掉了，
  弹窗里是纯文本

### 什么时候弹，什么时候不弹

| 情况 | 行为 |
|---|---|
| 从旧版升上来 | 弹一次，关掉之后记下"这一版看过了" |
| 同一个版本再启动 | 不弹 |
| **第一次安装** | 不弹（刚装上的人不需要看"这一版更新了什么"），但会记下当前版本 |
| 装回旧版 | 不弹——给回退的用户看"未来的更新记录"没有意义 |
| 这一版没有写给用户看的内容 | **整件事跳过**，绝不弹一个空框 |
| 版本号读不出来（例如自己改坏了 `pubspec.yaml`） | 不弹。宁可少弹一次也不猜 |

**⚠️ 一个已知的边角**：它靠"上次见过哪个版本"来判断，而**从没有记过版本号的旧版
（也就是第一版带这个功能的版本之前的所有版本）升上来时，第一次不会弹**——程序分不清
"刚装上"和"从更早的版本升上来"，这两种情况都只能选择不弹。自愈：跑过一次之后就开始
记了，下一个版本照常弹。

### 想再看一遍

命令面板（`Ctrl+K`）里搜「更新」——弹窗只弹一次，所以必须留一个随时找得到的入口，
不然等于做完就找不到。

### 版本号从哪来

程序自己不知道自己是哪个版本，而查版本要用 `package_info_plus` 这类**插件**
（插件会让 Windows 构建要求开发者模式，见 [`docs/开发须知.md`](开发须知.md) §6）。
所以是把 `pubspec.yaml` 本身打进包、读它的 `version` 字段：**版本号只有一个真相来源**，
不存在"忘了同步某个常量"这种静默失效。判断逻辑是纯 Dart
（[`lib/core/app_version.dart`](../lib/core/app_version.dart)），能单独测。

## 写作日历（选日期 + 热力图）

**界面上只有左侧栏那一个按钮**（日历图标），打开后右上角的 `月 | 年` 切换两种尺度：

| 怎么进 | 落在 | 因为 |
|---|---|---|
| 左键点侧栏的日历图标（提示文字是「月视图/年视图」） | **月** | 这个图标的本意是"选日期" |
| 命令面板（`Ctrl+K`）搜「热力图」 | **年** | 这个入口的本意是"看全年写得多不多" |
| 命令面板搜「选择日期」 | **月** | 同上，只是从键盘走 |

> 右下角状态栏原来还有一个 ▦ 按钮，和侧栏这个功能重复，**已经删掉**：
> 同一个对话框开两个常驻按钮，用户只会在两个之间犹豫点哪个。
> 想直接看年视图就走命令面板——那里两个尺度各有一条，是**搜**出来的不是摆出来的。

**月视图和年视图的对话框是一样大的**（同一个宽度、同一块固定高度的格子区），所以切换 `月 | 年` 时框体不跳。差别只在格子怎么摆：

- **年视图**：格子铺满整个宽度（53 列 × 14px），下面接「当日详细」
- **月视图**：格子 54px 铺在左边，右边那一栏放「当日详细」

**没悬停时「当日详细」显示"当前打开的那一天"**，不是一句"请把鼠标移上去"。默认状态才是最常看的状态——只写提示的话，那 200–480 像素在默认状态下纯属浪费。

**正文显示的是整篇，不是首行**：能放几行就放几行（行数是按面板的实际高度和字体行高**算出来的**，不是写死的），放不下的部分由 `Text` 加省略号。字号也比原来那条 42px 单行简要大一档。**点一下就跳过去**（对话框自动关掉）。

> ⚠️ 这里踩过一次：一开始用的是 `DiaryEntry.preview`，而它的定义就是"逐行找第一个非空行"——所以无论面板多大，都只可能显示第一段。想看全文必须用 `DayWriting.text`（整篇，逐行去掉 Markdown 标题符号），这是两个不同的东西。

### 想调大小？改这几个数（都在 `lib/ui/calendar_dialog.dart` 顶部那一段）

| 常量 | 现在 | 管什么 |
|---|---|---|
| `_yearCell` / `_yearGap` | 14 / 3 | 年视图格子大小与间距。**对话框宽度 = 53 ×（两者之和）+ 星期列宽**，所以调它等于调整个对话框的宽 |
| `_monthCell` / `_monthGap` | 54 / 6 | 月视图格子。它同时决定 `_monthGridWidth` 和格子区高度 |
| `_gridAreaHeight` | 388 | **两个尺度共用的格子区高度**——想加高整个对话框就调它 |
| `_sidePanelMinWidth` / `_sidePanelMaxWidth` | 200 / 480 | 月视图右边那一栏的宽度范围 |
| `_weekdayHeaderHeight` / `_weekdayHeaderGap` | 20 / 8 | 月视图星期表头那一条。**它算在 `_monthGridHeight` 里**——漏算会让框体溢出（踩过一次，正好差 22px） |

`build()` 里还有两次夹取：宽度不超过 `窗口宽 - 160`（窗口太小就不硬撑，改成格子横向滚动），右边那一栏不低于 200。

### 为什么是"两个尺度"而不是一个

年视图的格子只有 14px：**看**很清楚，**点**太难受。想把一年按能舒服点中的尺寸（54px）排下来要 2800px 以上，塞不进窗口。所以"看"用年、"选"用月——把两者合成一个入口，但保留两种尺度。

### 为什么换掉了 Flutter 自带的日期选择器

原来侧栏那个图标用的是 `showDatePicker`。换掉它的三个理由：

1. 它**不认识"这天写过没有"**——而选日期的时候最想知道的就是这个
2. 程序没配 `localizationsDelegates`（也不该为零星几个词引入 `flutter_localizations`），所以它内部的**月份名和星期表头是英文**
3. 日历和热力图读的是同一批数据、动作也一样，分成两个入口只会让人猜该点哪个

能选到的范围沿用原来的（**1970 到今年 +1**），所以这次合并没有改变"能选到哪一天"。

### 四条刻意的决定

| 决定 | 为什么 |
|---|---|
| **深浅按当天字数分 5 档**（0 / 1–99 / 100–299 / 300–699 / 700+） | 只分"写过 / 没写"信息量太小；而用心情决定颜色**没有唯一答案**（各家对"什么心情算什么色"根本不一致），和「宜忌」那类问题一样。**档位写在图例上**，不让用户猜——阈值是人定的，就该让人看见。两个尺度共用同一个映射 |
| **周一开头** | 和左侧列表的星期写法一致。两处不一致的话，看久了会觉得哪里不对，但说不出是哪 |
| **颜色只用主题令牌 + 透明度** | 不硬编码任何色值，深色模式自动跟着变（写死一套绿色系的话，深色下会糊成一片）。"没写过"（浅底）和"不在这个范围"（全空）用**不同**的画法，否则分不清"那天没写"和"那格不算数" |
| **右侧那一栏的底色用 `surfaceContainerLow`** | 第一版用了 `surfaceContainerHigh`——那**正好就是 `AlertDialog` 自己的底色**，画上去等于没画，右边看起来是一片空的。同一层级的令牌拿来当"卡片底"是看不见的，这是踩过一次的坑 |
| **格子按自然日逐个构造**（`DateTime(y, m, d + 1)`，不是 `add(Duration(days: 1))`） | 跨夏令时的时候 Duration 加法会跳天或重复。中国没有夏令时，但这个程序的数据格式是带时区的，逻辑上不该假设没有 |
| 月视图**固定 6 行** | 月份本身是 4/5/6 行，行数一变对话框高度就跳，翻月份时上下的东西会跟着抖 |

### 「写过」的定义，这里有一处既有分歧

两个视图用的定义都是**有内容**（复用 `DiaryEntry.isEmpty`：正文去空白、心情、天气、标签全都空才算空），判断收在 `lib/core/writing_stats.dart` 一处。

⚠️ 但侧栏那个「今天（已写）」徽标用的是**另一套**——`hasWrittenToday`，看"有没有这个文件"。一个空的 `.md`（手机同步过来的空文件就会这样，见 [`docs/手机写作.md`](手机写作.md)）会让两者给出**相反**的答案。**要不要把徽标也统一过来是另一个决定**——那会改动界面上已有的行为，所以没有顺手做。

### 还没有的

月视图**只支持鼠标**：没有 ←→↑↓ 走格子、PageUp/PageDown 翻月。自带的选择器有键盘操作，所以这一条算是换掉它的代价，记在 [`docs/开发须知.md`](开发须知.md) 的「已知限制」里。

## 每日提醒

到点如果**今天还没写**，让 Windows 弹一条通知：

```
┌────────────────────────────────┐
│ 日迹                           │   ← 名字和图标靠 AppUserModelID 注册表项
│ 今天还没写日记                  │
│ 点一下打开今天的日记            │
│ [ 打开日记 ]                    │   ← 点了就回到今天的日记
└────────────────────────────────┘
```

**默认关**。打开它意味着往系统里写东西，这种事必须用户自己点。入口在「⋮ → 每日提醒」和命令面板（搜「提醒」）。

**可以指定星期几**：默认每天，也能只留工作日（或者随便几天）。
没选的那天 Windows 根本不会启动它——所以"哪天会提醒"在任务计划程序里**一眼看得见**，
不用去读脚本。至少留一天：一天都不选这个功能就永远不会触发，与其让它变成一个哑掉的
状态，不如不让人取消最后一个。

### 它往系统里写四样东西（关掉时一样一样删掉）

| 写什么 | 干什么用的 |
|---|---|
| 一个计划任务 `riji-reminder` | 到点触发（**按周指定那几天**）。**程序不用常驻**——是 Windows 自己把它拉起来的 |
| `%APPDATA%\riji\remind.ps1` | 到点跑它：判断今天写没写，没写就发通知 |
| 注册表 `HKCU\...\AppUserModelId\lkczy.riji` | 让通知显示成「日迹」+ 程序图标，而不是某个进程名 |
| 注册表 `HKCU\Software\Classes\riji` | 注册 `riji://` 协议，让点通知能回到日记 |

**不需要管理员权限**：计划任务是当前用户的，注册表写在 `HKCU`。全部在计划和任务里可见、可手工删。

### 到点的时候，谁来说这句话

**两条路径，但一次只响一遍**：

| 情况 | 谁提醒 | 为什么 |
|---|---|---|
| **程序开着** | 程序自己弹一个对话框（「现在写」/「今天算了」） | 不用为了发条通知再交接一次进程；而且这时候你就在程序里，话可以直接说 |
| **程序没开** | 计划任务发 Windows 通知 | 没人能弹窗。系统通知是唯一能留在通知中心等你回来的东西 |

分工靠一个很笨但可靠的办法：脚本发通知之前先 `Get-Process` 看一眼程序在不在跑。
在跑就不发（交给程序），不在跑就发。**查不出来时按"没在跑"处理**——宁可多一条通知，
也不要一条都不弹。

程序内那个提醒还多两个限定：**只在这一天还没写、而且程序确实跨过了提醒时间**时才弹。
22 点才打开程序的人不该一开就被告知"今天还没写"——他打开就是为了写。
弹过一次就记下当天日期，之后不再弹（轮询每几秒一次，"到点了"这个条件会一直成立到当天结束）。

### 点通知之后发生什么

Windows 会拿 `riji://today` 起一个新进程。两种情况：

- **程序没开**：这个进程就是正常启动（本来就打开今天），直接就能写
- **程序开着**：新进程拿不到单实例锁，也**不用插件没法把已开的窗口调到前台**（见前面「单实例」一节），所以它留一张纸条（`%APPDATA%\riji\activation.txt`）就退出；正在跑的那个实例本来就在轮询磁盘（外部改动检查），顺手读走纸条、跳到今天、把光标放进正文

### 四条刻意的决定

| 决定 | 为什么 |
|---|---|
| **用计划任务，不用"程序常驻 + 内存定时器"** | 常驻要托盘图标（插件），而且和这个程序"打开、写、关"的设计冲突。计划任务的投递是可靠的：程序关着也能提醒，睡眠错过还会补跑（`StartWhenAvailable`） |
| **提醒日交给计划任务的 `-Weekly -DaysOfWeek`，不是"每天触发 + 脚本判断星期几"** | 没选的那天 Windows 根本不会启动它：省一次进程，而且"哪天会提醒"在任务计划程序里一眼看得见。也就不用把提醒日再存一份到脚本里（少一个会不一致的地方）|
| **判断"写过"的是脚本，不是程序** | 到点时程序可能根本没在跑。脚本读当天那个 `.md`，判定**和 `DiaryEntry.isEmpty` 对齐**：正文（去掉空白）或心情/天气/标签有一项非空。脚本带 `-DryRun` 参数，所以这份"镜像的判断"是**可验证的**（见 `docs/开发须知.md` §7） |
| **真通知，而不是弹自己的窗口** | 未注册的进程抢不到前台——弹窗只会出现在别人的窗口后面、再闪一下任务栏，几乎没用。Windows 通知是系统为这件事设计的：右下角、进行动中心、能带按钮。**但程序自己在跑时反过来**：它就在前台（或至少是你在用的那个程序），弹自己的对话框更直接 |
| **只在全部成功之后才把开关记下来** | 失败还把开关拨过去，界面会显示"已启用"而系统里什么都没有——到点不提醒，用户却以为已经开了。这是这个功能最要命的失败方式，有测试钉着 |

### 已知限制

- **只在 Windows 上**：计划任务和 WinRT 通知都是 Windows 的东西，其它平台这个入口整个不出现
- **改时间要按一下「改成 HH:MM」**：选完时间不会自动改系统——不然每动一下下拉框就起四个 PowerShell
- **"写过"有两套定义**：提醒用的是"有内容"（和日历一致），而侧栏徽标用的是"文件存在"。一个空的 `.md` 会让两者答案相反（见「写作日历」一节末尾）
- 通知的**归属名字**依赖那个注册表项；如果被别的清理工具删了，通知会显示成 AppID 本身。启动时的"对账"会把指纹不一致的重装一遍，但这种"项还在、内容被改"的情况它看不出来
- **程序开着但窗口被压在最下面**时，程序内那个对话框只是安静地等着你去点它——它没法把自己抢到前台（同「单实例」那一节）。反过来，如果程序**根本没开**，就一定会走系统通知那条路

## 日记加密

**默认关**。打开它意味着开始把内容加密，这种事必须你自己点。入口在「⋮ → 日记加密」，
命令面板里搜「加密」也有。

### 三种锁法

| 锁什么 | 磁盘上变成什么 | 怎么操作 |
|---|---|---|
| **整天** | 正文变成 `[正文已加密]`，整篇密文进 front matter | 光标随便放，「⋮ → 锁上这一整天」 |
| **一段（黑条）** | 那一行变成和原文**等长**的 `██████`，密文进 `enc-redactions` | 光标放到那一行，「⋮ → 锁上光标这一段」 |

**没锁的日子一个字都不变**：仍然是能用记事本直接打开的 Markdown。这是这套设计
最要紧的取舍——加密是给「不想让人看见的那几天」用的，不是给整本日记用的。

### 解锁

两条路，权限不同：

| 怎么解锁 | 能做什么 | 密钥留多久 |
|---|---|---|
| 「日记加密」里输口令 | 看、搜、锁、解锁、改 | 到你点「立即锁定」或者关掉程序 |
| 侧栏「解锁来搜索」 | **只能解密来搜索**，不能改任何文件 | 到你把搜索框清空 |

解锁之后，**底栏会一直显示「已解锁」**，点一下就能立刻锁回去——因为你走开一会儿
之后，屏幕上得有东西告诉你现在是什么状态。

锁着的内容在解锁前是**只读**的：正文改不了（心情、天气、标签仍然可以补），
所以不会出现「把黑条改坏、结果内容对不上」这种事。

### 恢复码

开启加密时会给你一串恢复码。**忘了口令时它是唯一的办法**——程序里没有后门，
也没有「找回密码」。抄在纸上、或者放进密码管理器；**不要**和日记放在一起。

### 它防谁、不防谁

| 场景 | 能不能防 |
|---|---|
| 笔记本丢了 / 硬盘被拆走 | ✅ |
| 同步到网盘、被云服务商或别人看到 | ✅ |
| 同一台电脑上的另一个 Windows 用户 | ✅ |
| **有人趁程序开着、而且已经解锁** | ❌（所以底栏那个「已解锁」要留意）|
| 木马 / 键盘记录 / 截图 | ❌ |
| **忘了口令又丢了恢复码** | ❌ 永久打不开 |

### 几处要知道的取舍

- **`chars`（这一天的总字数）是明文存的**，热力图和底栏的字数要用它。所以
  「哪天写了、大概写了多少」是公开的，锁住的是**内容**。
- 按段锁的黑条**和原文等长**，所以「这一段大概多长」也看得出来。
  将来若要做「填充到固定长度」，这两条要一起改。
- **手机和 Obsidian 打不开锁着的内容**（那正是加密的目的）。没锁的天照旧。
- 密码学细节（算法、密钥派生、格式、威胁模型）见
  [`加密设计.md`](加密设计.md)。

### 不想用了

「日记加密」里有「关闭加密…」。它会**先把所有锁着的天解开、写回明文**，
确认磁盘上真的没有锁着的内容之后，才删掉保险库文件——有任何一天解不开，
它会**拒绝关闭**并把原因说出来（先删密钥的话，那些内容就永久打不开了）。
### 程序锁（进入程序要口令）

在「⋮ → 日记加密」里打开「进入程序时需要口令」：

- 以后打开程序先看到锁屏，**看不到任何日记内容**（用和日记加密同一个口令）
- 闲置一段时间（默认 10 分钟）自动锁上；也可以随时按 **Ctrl+L** 立刻锁上
- 开了程序锁之后，"锁定"就等于离开程序；没开程序锁时，"锁定"只丢密钥，
  锁着的天照旧显示 🔒/黑条（不会看起来像数据没了）

**它挡住的是**：别人用你已登录的电脑点开这个程序。
**它挡不住的是**：绕过程序直接去翻日记文件的人 —— 没有加密的日子在磁盘上仍然是明文。
要挡住后者，靠的是把内容**加密**。

忘了口令可以用恢复码进；万一保险库文件丢了，锁屏上有一个「直接进入」的口子 ——
绝不会把你关在自己的日记外面。
## 历史版本与回收站

这两个是菜单里更"重"的功能，单独说明。

### 历史版本

**它挡的是哪一类损失**：备份挡的是"设备级"丢失（盘坏了、文件夹被误删，见「备份」），
历史版本挡的是"内容级"丢失——**已经落盘的内容被改掉了**。

在自动保存的程序里这一条格外重要，因为：

> 你在 Word 里可以「关闭而不保存」。这里没有这道闸门——文件在 900 毫秒内就提交了。

所以对已经存进去的内容，恢复途径只有两条：当前编辑会话里的 `Ctrl+Z`，
以及磁盘上留下的历史。前者重启就没了，后者是这个功能提供的。

**做这个功能时顺带修掉了一个会丢数据的 bug。** Flutter 的撤销栈记录 controller
的**每一次**值变化，不区分是用户敲的还是程序赋的；而本程序所有日期共用一个
controller，于是撤销栈里混着好几天的内容。实测后果是：**切到别的日期再切回来
按 `Ctrl+Z`，会把那一天的内容灌进当前这天，并在 900ms 后自动保存落盘**，
原内容没有任何副本。现在输入框子树会随正文版本重建（撤销栈跟着清空），
并且 `test/ui_test.dart` 里的「撤销不会跨日期」有回归测试守着——
那个测试在关掉修复之后确实会失败。

**什么时候留快照**（这里有个关键的设计约束）：

| 时机 | 原因 |
|---|---|
| **打开某一天时** | 这就是「我今天坐下来写之前，这篇是什么样」，整条历史里最有用的一份 |
| 编辑过程中距上次快照超过 **10 分钟** | 挡「写了半小时之后改坏」 |
| 点「留一份当前版本」 | 手动，不受时间限制 |
| **恢复历史版本之前** | 无条件留一份。没有它，「恢复」本身就会变成一次丢内容 |
| 内容与最新一份完全相同时 | **不留**。快照的价值在于记录另一个样子 |

> **快照的粒度必须比保存频率粗得多。** 自动保存是亚秒级的，如果按"每次保存前
> 留一份"来做，会得到一堆相隔一秒、彼此几乎相同的文件——看起来历史很丰富，
> 实际上没有一份有用，列表还会长到没法看。所以按**会话**和**时间网格**留，
> 而不是按保存次数。这也是为什么自动快照那条路径在绝大多数保存上
> 一个字节都不读：内存里记着"上次快照是什么时候"，十有八九一句话就返回了。

**存在哪**：`<日记根>/.history/2026-10-04/213045123-opened.md`。文件名自带
时刻和原因（`opened` / `auto` / `manual` / `before-restore`），所以**把文件
单独拷出来也自解释**。存的是**原始字节**而不是重新编码的结果——手工加过的
注释、程序还没认识的前置字段，都能原样恢复。

每天最多 30 份，超出时丢掉**第二份**（索引 0 那份是「打开时的样子」，最该保住）。

### 回收站

删除是**软删除**：文件被移到 `.trash`，内容一个字节都没少。回收站里能看、
能恢复、能永久删除（只有「永久删除」才真的抹字节，所以要二次确认）。

**恢复时如果那一天已经有内容了**（删完又写了新的），**绝不覆盖**：回收站里
那份会被另存为冲突文件，两边都保住，界面明确告诉你它去了哪。

删除会连带清掉那一天的草稿（否则下次启动会提示你恢复一篇已经删掉的日记），
但**保留历史快照**——那是这一天另一层独立的保护。

## 黄历悬浮卡片

**把鼠标停在左侧某一栏上约 0.65 秒**，右边会弹出一张这一天的黄历卡片；
**长按**同一栏也能弹出（手机上没有 hover，长按是唯一的入口，所以这个兜底不是可选项）。

卡片是**只读**的：包在 `IgnorePointer` 里，不会挡住底下的点击；鼠标移开或滚动列表就关掉。

### 这张卡片里有两类可信度完全不同的东西

这是这个功能最要紧的一点，所以界面上把它们分开显示：

| 内容 | 性质 | 能不能验证 |
|---|---|---|
| 干支（年/月/日）、冲煞 | **历法推算**，有唯一答案 | ✅ 能 |
| 宜、忌 | **择日学（传统历注）**，各家通书不同 | ❌ **不能** |

实测依据（同一天、两个独立实现）：

```
干支：lunar_python 与 cnlunar 在 730 天里 100.0% 一致（年/月/日三项都是）
宜忌：同一年里「完全一致的日子」是 0.0%
      「宜」条目交并比 10.3%、「忌」只有 3.9%
      2026-01-01 两天都列的只有「塞穴」「补垣」两个词
```

所以干支、冲煞是**可验证**的，而宜忌**没有唯一正确答案**——
它不是农历的一部分，是另一套体系。卡片上因此写着「宜忌是传统历注……
仅供参考，不是事实」，这一点不能省。

### 年干支用的是春节分界

`getYearInGanZhi()` 按**春节**分界（2026-02-05 已过立春、未到春节，仍是乙巳；
2026-02-18 才变丙午），和农历年一致，也和 cnlunar 的约定一致——所以它可被交叉验证。
另一派是**立春分界**（八字/命理用），两者在立春到春节之间那十几天会不同。
这里刻意选春节分界：它和界面上显示的农历年一致，不会出现「农历还写着腊月、
年干支却已经翻篇」的观感矛盾。

### 数据

| 项目 | 值 |
|---|---|
| 覆盖范围 | 公历 **2000–2060**（22281 天） |
| 文件 | `assets/huangli.tsv`，约 1.4 MB |
| 生成 | `tool/generate_huangli.py` |
| 插件 | **没有**。读取用 `rootBundle`，属于核心 Flutter |

范围外（比如 1990 年）**不显示卡片**——宁可没有，也不显示错的。

做成**资源文件而不是 Dart 源码**：两万多行的常量会让每次编译都变慢，
而资源文件是独立文件、不参与编译。

每一行是一天，从起始日**连续**排下来，所以不需要在数据里存日期：

```
年干支 \t 月干支 \t 日干支 \t 冲(地支) \t 煞(方位) \t 宜索引串 \t 忌索引串
```

宜忌用**两位 36 进制索引**指向词表（114 个词，写在 `lib/core/huangli_data.dart`）。
词表按 Unicode 排序而不是按出现顺序：这样它与年份范围无关，重新生成数据时
索引不会整体错位。冲那里存的是**地支**而不是生肖，生肖由 Dart 用固定的十二支
映射推出来——这样「冲 = 日支 + 6」这条不变量可以被测试直接验证。

### 生成时的自检

`tool/generate_huangli.py` 每次生成都会跑这三条不变量，不通过就拒绝出数据；
`test/huangli_test.dart` 在 Dart 侧对**全部 22281 天**再验证一遍：

- 日干支每天正好前进一位（六十甲子循环）
- 冲必须是日支的对面（相隔六位）
- 每一行的宜忌索引都能解析出词（没有越界被静默丢掉）

这些不需要第二个实现就能验证，而且是抓编码错误最有效的手段。

## 备份

日记是**唯一一份**，而且现在还会同步到手机——但**同步不是备份**：它会把误删和
误改一起复制到两台设备上。所以备份必须落在**第三个地方**。

### 怎么设

编辑区右下角**「更多」菜单 → 备份**：

| 项 | 说明 |
|---|---|
| 备份位置 | **必须你自己设**。没设之前「立即备份」是禁用的，旁边写着原因——不是藏起来 |
| 立即备份 | 可以填一句说明，会写进快照的目录名和清单里 |
| 从备份恢复 | 只恢复到**新文件夹**，绝不写回正在用的日记目录 |
| 打开备份文件夹 | 在资源管理器里定位 |

备份目录下是 `自动/` 和 `手动/` 两个子目录，每份快照里有一个 `备份清单.txt`
（时间、类型、来源、文件数、总字节，以及逐文件的路径 / 大小 / 修改时间）。
有了它，三年后打开一份快照，不依赖任何程序就能判断它是不是完整的。

**快照里进什么**：`2026/`（日记本体）、`.history/`（历史版本）、`.trash/`（回收站）。
**不进什么**：`.drafts/`、`*.tmp-*`、`.index.sqlite`、同步工具的标记目录。

> 注意这里和同步的忽略规则**方向相反**：`.history` 和 `.trash` 要**排除出同步**
> （每台设备各有一份，同步只会互相制造冲突），但**必须包含进备份**——
> 出错之后最想要的就是这些东西。

### 自动快照和手动快照

| | 什么时候做 | 保留 |
|---|---|---|
| **自动** | 关闭程序时。**一天至多一份**，而且内容没变就跳过 | 只保留最近 **30** 份 |
| **手动** | 你点「立即备份」 | **永不删除**（程序里没有任何代码路径会删它） |

那两道限制都是为了让「保留 30 份」真正等于"约一个月的写字日"：不加"一天至多一份"，
开关十次程序就产生十份，30 份只覆盖三天；不加"内容没变就跳过"，只是打开看看
也会留下一份完全一样的快照。

清理旧自动快照时，程序**只删自己建的那些**，而且删之前会确认目录里确实有
`备份清单.txt`——**一个认不出来的目录，宁可多占空间也绝不删**。手动快照所在的
`手动/` 目录，保留策略根本不会去看。

### 它挡得住什么、挡不住什么

| 备份位置 | 挡得住 | 挡不住 |
|---|---|---|
| 另一块盘 / 移动硬盘 | 误删、误改、单块盘坏掉 | 火灾、失窃这类"两台设备一起没" |
| **和日记同一个盘** | 误删、误改 | **这块盘坏掉** |

界面会把这件事如实说清楚：同盘时明确提示"挡不住这块盘坏掉"，并补一句
**两个盘符也可能是同一块物理盘**——这一点程序判断不了，所以只能提示、不能保证。
被拒的只有一种情况：备份位置和日记目录**互相包含**（会递归复制，而且会被
Syncthing 同步到手机）。

### ⚠️ 上传云盘的节奏 = 你的数据安全窗口

如果备份只落在电脑上的另一个文件夹，那么**真正防住盘坏的是"把备份传到云盘"
这一步**。程序看不见云盘，无法知道你什么时候传过，所以这个节奏只能你自己把握：

- 一个月传一次 → 盘坏时最多丢一个月
- 想省掉手动这一步：如果云盘客户端有本地同步文件夹（OneDrive、坚果云这类都有），
  直接把备份位置指向它。代价是你在本地删旧快照时，云端那份也会跟着删
  （有些客户端保留历史版本，有些不会）

## 更改日记位置

入口在编辑区右下角的**「更多」菜单 → 日记存储位置**。行为和安全保证：

| 保证 | 说明 |
|---|---|
| **只复制，从不移动** | 勾选复制后，原文件夹一个字节都不会被改动。确认新位置没问题后，删不删旧文件夹由你决定 |
| **拒绝覆盖** | 目标位置只要存在同名文件，复制立刻中止。所以「复制」在任何情况下都不会毁掉目标位置原有的内容 |
| **复制后逐个校验** | 比对每个文件的大小。校验不过就报错，且**设置不会被改动**——程序仍然指着原来的位置 |
| **切换前先落盘** | 正在写的那句话会先存回原位置，再开始复制，避免最后一段内容丢失 |
| **设置最后才写入** | 保证「设置」永远只描述一个确实可用的位置。任何一步失败，设置都不变 |

界面会实测而不是猜测：目标能不能写（真的建一个临时文件再删掉）、里面已经有几篇日记、
有没有别的 `.md` 文件、磁盘是可移动还是网络盘。

**已知的取舍**：没有调用系统原生文件夹选择器，因为那需要插件，而插件在 Windows 上要求
开启开发者模式。所以是「自己用 `dart:io` 列目录的内置选择器 + 手输路径」，
不如资源管理器顺手。

### 构建陷阱：图标字体子集不会被增量重建

Flutter 打包时会把 `MaterialIcons-Regular.otf` 从 1.6MB 裁剪到只剩程序用到的字形
（本项目约 4.7KB）。但**这个裁剪结果在增量构建里不会重新生成**：

```
第一次完整构建   → 字体含当时用到的 22 个图标
之后新增 3 个图标 → 增量构建，字体仍是旧的 → 那 3 个图标在界面上是空白方框
```

构建**不会失败、不会报警告**，只是图标不见了。这个坑真实踩过：外观菜单的
三个图标（跟随系统/浅色/深色）全部不可见，而同一版本里其它 22 个图标完全正常。

两道防线：

```powershell
# 1. 用脚本构建（内部强制 clean）
powershell -File tool\build_release.ps1

# 2. 单独审计字体覆盖（会列出代码里用到但字体里没有的每一个图标）
python tool\icon_audit.py `
  <flutter>\packages\flutter\lib\src\material\icons.dart `
  lib `
  build\windows\x64\runner\Release\data\flutter_assets\fonts\MaterialIcons-Regular.otf
```

审计输出必须是 `app icons MISSING : 0`。

**顺带一个已知的坑**：`Icons.info_outline` 和 `Icons.info_outlined` 这两个码点
即使在完整构建里也会被裁掉（用哪个变体都一样），是 Flutter 图标字体自身的缺口。
不要用它们；`tool/icon_audit.py` 能查出这类问题。

## 双端同步

**不要自己写同步服务。** 二选一：

- **Syncthing** —— 实时、免费、无云、端到端加密；手机端用 Syncthing-Fork。
- **私有 git 仓库** —— 多一层版本历史和后悔药，适合定时 commit。

同步的就是上面那个日记根目录。必须忽略：

```
.index.sqlite        （将来若引入索引）
.drafts/
.history/
.trash/
*.tmp-*
```

`.history/` 和 `.trash/` 也必须忽略：它们是**本机的操作痕迹**，同步它们只会
让两台设备互相制造冲突文件，白白把容量和噪音翻倍。（`DiaryPaths.syncIgnorePatterns`
里有完整列表。）

同一天在两台设备上都被改过时，同步工具会保留双方版本。程序会把冲突文件列出来让你手动合并，
**不会替你决定保留哪句话**。

## 几个刻意的取舍

**关于加密：程序不做加密，日记是明文。**
你明确选择了「不需要加密」。既然这是个清醒的决定，这里就不写任何暗示"有保护"的话：

- 日记以**明文**存放在磁盘上（`.md` 文件，`type` 一下就能看）
- 程序**不提供**任何加密、口令或访问控制
- 安全性完全取决于**你所在环境的访问控制**：谁能登录这台电脑、谁物理接触得到它、
  系统盘有没有开 BitLocker、备份和云盘上那份谁能看见

程序**没有权限查询 BitLocker 状态**（`Get-BitLockerVolume` 需要管理员），所以磁盘
到底有没有加密，程序不知道、也无法保证；想确认可以在管理员 PowerShell 里跑
`manage-bde -status`。更改日记位置时程序会提醒这一点。

**手机同步会引入两个额外的、程序无法验证的前提**：

1. **手机本身的存储加密状态**
2. **手机厂商的云备份范围** —— 如果它把 `Documents/` 一起备份上去，
   日记就去了一个"全盘加密"管不到的地方

这两条只能你自己在手机上确认，见 [`docs/手机写作.md`](手机写作.md)。

**为什么一天一个文件，而不是一个数据库？**
文件粒度就是同步粒度，双端冲突面天然最小；纯文本几十年后依然能读；数据和程序解耦。
数据库只做索引和缓存，不是唯一真相来源。

**为什么不引入 SQLite？**
数据量小到可以忽略：一年 365 个文件，写十年也才 3650 个，全量扫描就是毫秒级。
少一个依赖就少一处会坏的地方。真到了需要索引的那天再加，索引是可再生的。

**为什么零插件（连 `path_provider` 都不用）？**
Flutter 为插件建符号链接要求 Windows 开启开发者模式，而开开发者模式需要管理员权限。
只为定位一个默认目录付这个代价不值得——用环境变量就够了。

**为什么深色模式几乎没改组件代码？**
因为界面里所有颜色从一开始就走 `theme.colorScheme.*` 令牌，全项目只在
[`lib/ui/theme.dart`](../lib/ui/theme.dart) 里硬编码了 1 个种子色（其余 30 处全是令牌引用）。
换一个 `ColorScheme`，所有组件自动跟着变。这不是运气，是「不写死颜色」这条纪律的直接回报——
如果当初随手写了 `Colors.grey`，现在就要逐个组件去改，还一定会漏。

**为什么正文用 TextField 而不是富文本编辑器？**
日记的价值在内容不在排版。所见即所得编辑器会带来格式转换、粘贴污染、
导出失真一整类问题，而收益接近于零。Markdown 源码本身就是最好的格式。
