# 开发须知

改这个项目之前先读这份。

它不是架构说明（架构在代码注释里，用法在 `README.md` 里），而是**"不读就会付代价"的东西**。下面每一条都是真实发生过的，标注了当时的代价。

## 0. 验收标准（这个项目的门槛比一般项目高）

```
flutter analyze                     → 必须 No issues found
flutter test                        → 必须全过（当前 513）
改了界面                            → 必须重建 + 图标审计 MISSING : 0 + 真机启动
真实文件 I/O 的测试                 → 必须是普通 test()（见第 2 节）
安全相关的保护                      → 必须做反向验证（故意去掉保护，确认测试会失败）
```

一条命令跑前两项：**`tool\check.ps1`**。

**反向验证不是可选项。** 这次会话做了 3 次，**其中 1 次发现测试是空转的**：修剪逻辑的测试用 `i % 28` 生成目录，35 次循环只产生 28 个，**根本没到 30 的上限**，于是那条测试无论代码对错都会通过。**去掉保护后它照样通过**，才发现问题。

判断"测试有没有牙齿"的唯一办法就是：**把被保护的东西故意破坏掉，看测试会不会红。**

## 1. 会「静默爆」的七类坑 ⭐

这些最危险，因为**改了不报错**，只在特定条件下才暴露。这一轮已经栽过两次。

**1.5、1.6、1.7 是后来补的**（1.5 / 1.6 是 2026-10-03 实现窗口几何时挖出来的，1.7 是实现命令面板时挖出来的）。1.5 和上面几条不同：**它会当场让编译失败，不会静默爆** —— 真正的代价是**几个小时都在查一个跟业务逻辑毫无关系的报错**。1.6 和 1.7 则完全符合"静默爆"的定义，而且**不需要任何特殊条件**就会踩。

### 1.1 图标字体被裁剪过 → 新图标在 release 里变成空白

`MaterialIcons-Regular.otf` 是**按实际用到的图标生成子集**的。

- 用一个新的 `Icons.xxx` → **release 里那个图标是空白方块**，没有任何报错
- 只有 `tool\build_release.ps1` 里的图标审计（`app icons MISSING : 0`）能发现
- 而且**增量构建不会重新生成字体**，必须走那个脚本（它含 `flutter clean`）

**做法**：加图标前先确认它在已用集合里；加完必须重建并看审计。

### 1.2 保存「旧名字」的常量是地雷 → 迁移静默失效

程序从 `myDiary` 改名为 `riji` 时，批量替换把

```dart
const String _legacyAppDirName = 'myDiary';   // 指向"改名之前"的目录
```

**一起改成了 `'riji'`**。后果：设置迁移会去新目录里找一个并不在那儿的旧设置 → **静默失效** → 不报错、不崩，只会在某次重启后让用户发现程序打开了一个空白日记（数据其实一个字节都没少）。

**当时的代价：489 个测试全过**。测试覆盖不到这条路径。

**做法**：
- 凡是保存"历史名字"的常量，注释里必须写明**它为什么必须保持旧值**
- 必须有一条测试**直接断言那个字面量**（见 `test/settings_migration_test.dart`），并对它做反向验证

### 1.3 `.gitignore` 里写死名字的规则，盖不住改名后的文件

`.gitignore` 里原有一条 `/riji.lnk` —— 它是从 `myDiary.lnk` 被批量替换来的，**覆盖不到 `日迹.lnk`**。如果不发现，移出跟踪后下一次 `git add -A` 会把它重新加回来。

**做法**：`.gitignore` 里用**通用模式**（`*.lnk`），不要写具体文件名。

### 1.4 单位混淆：窗口几何存物理像素 → 非 100% 缩放下二次放大，而且跨启动累积

**背景**：`Win32Window::Create` 的 `origin` / `size` 参数是**逻辑单位（DIP）**，
它在内部会乘一次缩放系数（`win32_window.cpp`）：

```cpp
double scale_factor = dpi / 96.0;
HWND window = CreateWindow(
    window_class, title.c_str(), WS_OVERLAPPEDWINDOW,
    Scale(static_cast<int>(ClampToLong(origin.x)), scale_factor),
    Scale(static_cast<int>(ClampToLong(origin.y)), scale_factor),
    Scale(static_cast<int>(ClampToLong(size.width)), scale_factor),
    Scale(static_cast<int>(ClampToLong(size.height)), scale_factor),
    nullptr, nullptr, GetModuleHandle(nullptr), this);
```

**所以**：把 `GetWindowPlacement` 拿到的**物理像素**原样存下来、下次再原样传回
`Create` → **会再乘一次** → 150% 缩放下 1280×720 变成 1920×1080，而且**每次启动
都会再放大一次**（累积）。

**正确做法**：

| 环节 | 做什么 |
|---|---|
| 保存 | `GetWindowPlacement` 拿到的是物理像素 → **除以 `GetDpiForWindow(hwnd) / 96.0`** → 存**逻辑单位** |
| 读取 | 解析逻辑单位 → 校验 + 夹取 → **原样交给 `Create`**，让它自己乘那一次 |

夹取坐标时要注意：`MonitorFromPoint` / `GetMonitorInfo` 用的是**物理像素**，
所以要先换算成同一套单位再比较。

**⚠️ 这条已经实现了**（2026-10-03）：读写逻辑在
`windows/runner/window_state.h` / `window_state.cpp`，启动读取在 `main.cpp`，
`WM_CLOSE` 里保存（**不是 `WM_DESTROY`** —— 那时 HWND 已无效）在
`win32_window.cpp`。文件是可手改的纯文本
`%APPDATA%\riji\window.txt`，一行 `x y 宽 高 是否最大化`。

**易错点**（实现时踩过的，改这部分前先看）：

- 最小化**不算**最大化。用户最小化后关掉程序，下次该按正常尺寸出现，
  而不是一启动就是最小化（那看起来像没启动）
- 存的是 `rcNormalPosition`（**还原后**的矩形），不是最大化时的尺寸。
  最大化时 `GetWindowPlacement` 本来也永远给正常状态的位置
- 只在**关闭时**写盘。不要挂到 `WM_SIZE` 上 —— 拖动窗口会连发上百条消息
- 读取失败（文件不存在 / 内容不合法 / 读不动 / 写不进）一律**静默回退**
  `(10,10) 1280×720`，绝不阻止启动

**附带好处**：存逻辑单位之后，**DPI / 缩放变化不再是限制** —— 逻辑单位不随缩放变，
150% 和 100% 下窗口的观感大小一致。所以注释里要写的是
"**这是逻辑单位，不能当物理像素用**"，而不是"这是个已知限制"。

**⚠️ 为什么最容易漏**：开发机是 **100% 缩放**（本机 DPI 96，`scale_factor == 1.0`），
乘一次和乘两次的结果**完全一样** → **这个 bug 在本机永远复现不了**。
凡是"只在非默认缩放/非默认 DPI 下才暴露"的换算，都要先假设它在开发机上是隐形的。

**实测（2026-10-03，本机 100% 缩放）**：真机跑了 6 条（首次运行、垃圾内容、
屏幕外坐标夹取、程序化搬窗后重启比对、最大化、最小化），全过。
**但那一条"非 100% 下二次放大"在本机依然无法真机复现** —— 它是靠**手工核算**
五个缩放（100 / 125 / 150 / 175 / 200%）确认的：存→读→`Create` 只乘一次，
5/5 精确往返，其中 4/5 个缩放能暴露"多乘一次"。
**手工核算不等于真机实测**，真正的非 100% 行为仍然没有在真机上验证过。

### 1.5 「没有 BOM 的 UTF-8 中文源文件」→ `C4819` 被 `/WX` 升级成 `C2220`，编译直接失败

**这条和上面几条不一样：它当场就把构建打红，不会静默爆。** 代价不是"悄悄错"，
而是**几个小时都在查一个跟业务逻辑毫无关系的报错** —— 报出来的东西长这样，
完全看不出跟"编码"有关系：

```
window_state.h(24,1): error C2059: 语法错误:“}”
window_state.h(24,1): error C2143: 语法错误: 缺少“;”(在“}”的前面)
```

**机理**：

- `windows/CMakeLists.txt` 里是 **`/W4 /WX`**（警告即错误）
- 本机**代码页 936**（简体中文 ANSI），MSVC 读**没有 BOM 的** UTF-8 源文件时
  按 CP936 解码 → 里面的中文报
  `warning C4819: 该文件包含不能在当前代码页(936)中表示的字符`
- `/WX` 把它升级成 `error C2220` → 编译直接失败
- 要紧的是：**中文注释会被解码器当成乱码字节**，进而把语法搅乱，
  于是真正的报错出现在**离原因很远的地方**（上面那两行 C2059/C2143 是**症状**，
  不是原因）

**⚠️ 它是这次改 `windows\runner\` 时引入的，不是一直潜伏着的**（这一点我一开始写错过，
已按下面的取证更正 —— 记在这里是因为"把结论写得比证据强"正是这份文档要防的事）：

| | 改之前（`bd2793c^`） | 改之后 |
|---|---|---|
| `main.cpp` | **有 BOM**（首次提交 `e27ccc0` 起就有，全程没被去掉过） | 仍**有 BOM** |
| `win32_window.cpp` | **没有 BOM，而且一个非 ASCII 字节都没有** | 有 BOM，1421 个非 ASCII 字节 |
| `win32_window.h` | 没有 BOM，纯 ASCII | 有 BOM，324 个非 ASCII 字节 |
| `flutter_window.cpp` | 没有 BOM，纯 ASCII | 未动 |

**实测取证（三种方法交叉一致）**：

- **编译**：在 `git worktree` 里 checkout `bd2793c^`（**原封不动**）真跑一次
  `flutter build windows --debug` → `BUILD_EXIT=0`、**C4819 出现 0 次**、
  C2220 0 次、error 0 次。**改之前编译是干净通过的。**
- **文件字节**：worktree 里用 .NET `ReadAllBytes` 读前三字节 →
  `main.cpp` 是 `EF BB BF 23 69 6E 63 6C`（BOM + `#incl`），
  `win32_window.cpp` 是 `23 69 6E 63 6C 75 64 65`（`#include`，无 BOM）
- **git blob 字节**：`git cat-file blob <rev>:<path>` 重定向到文件后读字节，
  结论与上面一致

**⚠️ 取证方法本身也有坑（我第一次就栽在这里，并因此写错了一版结论）**：
PowerShell 的 `>` 会**重新编码**输出（PS 5.1 默认 UTF-16LE），所以
`git show HEAD:... > file` 读到的**不是** blob 的原始字节。
可靠做法只有两种：`git worktree add` 之后读真实文件，
或者让 **`cmd /c` 自己重定向**到文件（`cmd /c "git cat-file blob <rev>:<path> > out.bin"`）。

**实际上 C4819 只出现在这次新加了非 ASCII 内容的 5 个文件上**：
`main.cpp`、`win32_window.cpp`、`win32_window.h`、`window_state.cpp`、`window_state.h`。
同一轮里 `flutter_window.cpp` / `utils.cpp` / `Runner.rc` 都没有报警告 ——
因为它们保持纯 ASCII，**根本没机会触发**。所以这条坑在这台机器上是由
**"给源文件新加中文注释（以及 `⚠️` / `→` 这类字符）"**触发的，与历史代码无关。
**好消息是规则因此更简单**：原本就是 ASCII 的文件，只要一直保持 ASCII 就永远安全。

**做法（工作流规则，必须遵守）**：

1. `windows\runner\` 下凡是含中文的源文件（`.cpp` / `.h`）**必须带 UTF-8 BOM**
2. ⚠️ **`edit` 工具会吃掉 BOM** → **改完这些文件后，必须先跑
   `tool\fix_runner_bom.ps1` 再构建**，否则编译不过
   （脚本是幂等的；只处理确定是 UTF-8 的文件，遇到 GBK 文件会跳过而不是写坏它）
3. 想确认是不是这个坑：搜 `warning C4819`

**验证过**：故意去掉 BOM → C4819 出现；`fix_runner_bom.ps1` 补回 → C4819 归零、
构建通过；并确认 **BOM 确实进了 git blob**（不是只在工作区），
否则别人 clone 下来照样编译不过。

**例外**：`Runner.rc` 没有 BOM 是**正常的** —— 它本来就有
`#pragma code_page(65001)` 自己声明了 UTF-8，不要"顺手"给它加 BOM。

### 1.6 有符号 / 无符号坐标 → 副屏在主屏左边或上边时窗口跑到屏幕外

和 1.4 是**同一族**（都是"坐标/单位的类型转换把窗口送到屏幕外"），但这条
**不需要任何特殊条件**，只要有人把第二块显示器放在主屏的**左侧或上方**就会踩。

**背景**：`Win32Window::Point` / `Size` 原来是这样定义的：

```cpp
struct Point {
  unsigned int x;
  unsigned int y;
  Point(unsigned int x, unsigned int y) : x(x), y(y) {}
};
```

多显示器下副屏可以在主屏左侧/上方，此时 x / y 是**负数**
（`GetWindowPlacement` 给出的也是负值）。负数塞进 `unsigned int` 之后是巨大的
正数，`Create` 里再 `static_cast<LONG>(origin.x)` → **窗口被放到屏幕外**。

**当时的代价**：不会有任何报错（`static_cast` 在超范围时是实现定义的，
Release 下就是回绕）。这件事之所以一直没炸，只是因为**这台机器只有一台显示器**。

**做法**：

- 坐标用**有符号**类型存（现在是 `long long`）
- 传给 `CreateWindow` 之前**显式夹取**到 `LONG` 范围
  （`win32_window.cpp` 的 `ClampToLong`），不要用 `static_cast` 硬转

**这条无法在这台机器上验证**（只有一台显示器）。想确认多显示器行为，
必须接上副屏、且**把副屏放到主屏左边或上边**再试 —— 右侧/下方的副屏
不会给出负坐标，测不出这个 bug。

### 1.7 全局快捷键绑在了错的层 → 一半的输入框里不生效，而且不报错

**现象**：`Ctrl+K` 在正文里能唤出命令面板，点一下左侧的搜索框、或者去心情 / 标签
输入框里打字，再按就没反应了。用户会以为"这个快捷键时灵时不灵"——
实际上它一直**很规律**：只在写作区里有焦点时生效。

**机理**：Flutter 的键事件从**主焦点节点向上冒泡**，只经过它的**祖先**；
兄弟子树之间不传递。

```
HomePage                          ← ✅ 绑在这里，谁的焦点都能命中
├── EntryListPanel（搜索框）        ← 从这里的焦点冒泡，路过 HomePage
└── EditorPanel
    └── 正文输入框                 ← 从这里的焦点冒泡，同样路过 HomePage
```

把 `CallbackShortcuts` 放进 `EditorPanel` 里，它就只盖住写作区：从侧栏搜索框出发的
键事件永远不会走进那个子树。**不会抛异常、不会有警告**，只是半个程序里不好使。

**做法**：全局快捷键绑在**所有相关输入框的共同祖先**上（这里是 `HomePage.build`
的最外层），而不是绑在某个面板里面。

**⚠️ 反面同样要注意（这一条是推论，没有实测）**：**不要**绑到 `MaterialApp`
外面（`app.dart`）。`showDialog` 弹出的对话框是 `Navigator` 的**兄弟路由**，
绑得比 `HomePage` 还高的话，对话框会成为它的后代 —— 在命令面板自己的输入框里
按 `Ctrl+K` 会再叠一层。
实测到的是它的另一面：绑在 `HomePage` 里时，面板自己的输入框里按 `Ctrl+K`
**不会**叠层（面板开着再按一次，仍然只有一个面板）。

**守卫**：`test/ui_test.dart` 的「侧栏搜索框有焦点时，Ctrl+K 照样能唤出面板」。
它先断言搜索框**真的**拿到了焦点，再按 `Ctrl+K`。
**反向验证过**：把 `CallbackShortcuts` 挪进 `Expanded(child: EditorPanel(...))`
里面，这条立刻变红 —— 所以它不是在空转。

## 2. 测试环境的三个坑

### 2.1 真实文件 I/O 不能用 `testWidgets`

`testWidgets` 跑在**假异步**环境里：`await` 真实 `dart:io` 的 Future **永远不会返回**，`--timeout` 也救不了（它挂住的是整个测试）。

**做法**：碰真实文件的测试用普通 `test()`。参考 `test/backup_drill_test.dart`、`test/fs_diary_store_test.dart`。

### 2.2 长命的 periodic 定时器不能由 controller 持有

第一版把自动重载的 `Timer.periodic` 放在 `DiaryController` 的构造函数里，**全套测试挂了 78 个**：

```
Pending timers: Timer (duration: 0:00:03.000000, periodic: true)
A Timer is still pending even after the widget tree was disposed.
```

因为 `testWidgets` 在 widget 树销毁后会检查有没有还挂着的定时器，而测试里创建的 controller **通常不会被 `dispose`**。

**规则**：**定时器由界面（widget 树）持有，随树销毁**；controller 只暴露"可以被调用"的方法（例如 `checkExternalChange()`）。参考 `home_page.dart` 里的 `_externalWatchTimer`。

### 2.3 验证 GUI 启动**不要用固定 sleep**

用 `Start-Sleep -Seconds 12` 判断"程序没起来"，报了假警报 —— 实际是冷启动比 12 秒慢。

**做法**：**轮询进程直到出现或超时**。假警报会让人去修一个根本不存在的问题。

```powershell
$app = $null
for ($i = 0; $i -lt 140; $i++) {
  Start-Sleep -Seconds 2
  $app = Get-Process riji -ErrorAction SilentlyContinue | Select-Object -First 1
  if ($app) { break }
}
```

## 3. PowerShell 5.1 的三个坑（这个项目栽过多次）

### 3.1 `.ps1` 必须带 UTF-8 BOM

没有 BOM 时，PS 5.1 按 ANSI 读文件，**里面的中文会变成解析错误**（不是显示乱码，是直接语法报错）。
`tool\* .ps1` 目前都带 BOM —— 用脚本改它们时**必须保留 BOM**（参考 `tool\build_release.ps1`）。

### 3.2 双引号字符串里不能再套双引号

```powershell
"  " + $(if ($x) { "有 $x" } else { '没有' })    # ✗ 语法错误
'  ' + $(if ($x) { '有 ' + $x } else { '没有' })  # ✓ 单引号 + 拼接
```

这个坑本项目栽过两次。

### 3.3 `-match` 是**大小写不敏感**的

```powershell
$an -match 'issues found'    # ✗ 会匹配上 'No issues found!'，把通过判成失败
```

**做法**：判断命令成败**优先用退出码**（`$LASTEXITCODE`），不要匹配输出文字。`tool\check.ps1` 就是按这个写的。

## 4. 批量文本替换的铁律

**必须排除二进制文件。** 这一轮把 `日迹.lnk` 当文本做了替换 —— `.lnk` 是二进制，替换后**快捷方式直接损坏**（双击报"没有关联的应用程序"）。

**做法**：替换前先列文件、按扩展名**白名单**过滤（`.dart .yaml .md .ps1 .py .json .cpp .h .rc .txt` …），并且**逐个保留原文件的 BOM 状态**。

**另外**：替换后要检查**文件名**，不只是文件内容 —— 这次 `myDiary.bat` 的内容改对了、文件名没改，导致脚本指向一个不存在的 exe。

## 5. git 操作的两个坑

### 5.1 非 ASCII 路径会被加引号转义

```powershell
git ls-files | Select-String '\.lnk$'     # ✗ 显示"无"（行尾是 `"` 不是 `k`）
```

git 默认把非 ASCII 路径输出成 `"\346\227\245..."`。

**做法**：先 `git config core.quotePath false`；确认删除/移出时**至少用两种方式交叉确认**，并且**确认磁盘上的文件还在**：

```powershell
git ls-files | Where-Object { $_ -match '\.lnk$' }   # 树里还有吗
git status --short                                    # 暂存区状态
Test-Path '日迹.lnk'                                  # 磁盘上还在吗
```

### 5.2 提交前扫一遍隐私

**一旦提交，用户名就永远留在历史里了。** 提交前：

```powershell
git grep -l '旧用户名' HEAD        # 树里有没有
git ls-files | Select-String '\.lnk$'   # 有没有本机相关的生成物混进来
```

## 6. 改动的既定原则（别被"顺手优化"掉）

- **绝不静默覆盖**：检测到外部改动时，两个版本都保留，把选择权交给用户
- **禁用而不是隐藏**：做不到的功能要**显示出来并说明原因**（比如没设备份位置时「立即备份」是灰的，旁边写着为什么）
- **回退用信息色，冲突用错误色**：区别在于"有没有丢东西"
- **同步忽略名单**和**备份排除名单**是**相反**的两份 —— `.history` / `.trash` **不同步**（每台设备各一份）但**必须备份**。别"顺手统一"掉
- **零插件**：数据是纯文件，任何工具都能读写。**加任何带 Windows 实现的插件都会让 Windows 构建失败**（需要开发者模式/symlink）
- **不硬编码颜色**：只用主题 token

## 8. 发布流程

```
tool\build_release.ps1            # flutter clean + 构建 + 图标审计（MISSING 必须 0）
组装发布包                         # ⚠️ 必须带三个 VC++ 运行库

真机启动验证                       # 用**包里的** exe 起，顺带证明包自包含
```

**运行库来源查法**（`riji.exe` 依赖它们，而 Release 目录里没有）：

```
dumpbin /dependents riji.exe
```

**注意**：包里那三个 DLL 可能**比目标机器 System32 里的旧**（这台机器上是 14.44 vs 14.51）。这不影响使用（程序用 14.44 工具集构建，要求 ≥14.44；CRT 同一大版本内二进制兼容），而且程序目录优先。

`tool\build_release.ps1` 里的 `D:\Dev\flutter` 可以用环境变量 `FLUTTER_ROOT` 覆盖。

## 9. 环境事实（这台机器）

- **`github.com` 间歇不可达**（`git ls-remote` 成功过，但用时可长达 22 秒；`objects.githubusercontent.com` 直接连不上过）
  **大文件下载的绕法**：走 GitHub **API 的资产端点**
  ```
  GET https://api.github.com/repos/<owner>/<repo>/releases/latest
  → assets[].url  +  Accept: application/octet-stream
  ```
  （`browser_download_url` 走被封的 CDN，`assets[].url` 走能通的 API）
- **国内镜像实测可用**：`maven.aliyun.com`（Android 依赖）、`pub.flutter-io.cn`、`storage.flutter-io.cn`
- **`manage-bde` / `Get-BitLockerVolume` 需要管理员** → 程序无法验证磁盘加密状态，只能提示
- **PowerShell 执行策略是 `Restricted`，`.ps1` 直接跑会被拒**
  （本机只有 Windows PowerShell 5.1，没有 `pwsh`；所有 scope 都是 `Undefined`）。
  所以 `tool\check.ps1` / `tool\build_release.ps1` 必须这样跑：
  ```
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File tool\check.ps1
  ```
  `-ExecutionPolicy Bypass` 只对**这一个进程**生效，不改机器设置。
  报错长这样，和脚本本身无关，别去改脚本：
  ```
  无法加载文件 ...\tool\check.ps1，因为在此系统上禁止运行脚本。
  ```
- **⚠️ 不要用 `Get-Content` / `Set-Content` 改本项目的 `.md` / `.dart` 文件。**
  PS 5.1 把没有 BOM 的 UTF-8 当成本地 ANSI 代码页读，一次
  `(Get-Content x -Raw) -replace ... | Set-Content x` 就能把整个文件变成乱码
  （2026-10-03 真的这么毁掉了 `README.md` 和本文件，只能 `git checkout` 重写一遍）。
  文本替换一律走编辑器的补丁方式，或者显式指定编码：
  `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)`。
  这和 3.1 是同一个根因，只是波及的不止 `.ps1`。
- **这个会话没有交互桌面**：进程能起、有窗口句柄，但 `GetForegroundWindow()` 返回 0，
  截图（`CopyFromScreen`）取不到内容。**"视觉确认"这类验证在本会话做不了**——
  不要因为截不到图就以为程序没渲染。
- **窗口几何在无交互桌面的会话里会漂**（2026-10-03 实测）：同一份 exe 前后起两次，
  `%APPDATA%\riji\window.txt` 从 `137 89 1043 731 0` 变成 `457 236 1569 1086 0`
  （屏幕 2560×1440、DPI 96，没有缩放，所以不是 1.4 那个换算问题）。
  **功能本身是好的**：载入什么就是什么（`GetWindowRect` 与文件逐值相等），关闭后
  原样写回，连测两次稳定。**原因没有查明**——这一轮只改过 `Runner.rc` 里的两个版本
  字符串，几何代码一行没动（`git diff` 可查），所以怀疑是这个会话的窗口管理器给的
  矩形，不是代码。**要验几何就在有真实桌面的会话里验，别把这里的数字当基准。**
- 单实例锁在 `%APPDATA%\riji\instance.lock`；设置在同目录的 `settings.json`
