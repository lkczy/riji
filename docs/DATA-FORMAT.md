# 日记数据格式规范 v1

> 本文件是 riji 的**唯一不可逆约定**。代码可以重写，UI 可以换框架，但一旦写了几年日记，
> 数据格式就不能再动了。所以它优先于一切实现细节。

## 核心原则

1. **Markdown 文件是唯一真相来源。** 任何数据库、索引、缓存都只是派生物，删掉后必须能
   仅凭文件完整重建。程序死了，日记依然能用记事本打开。
2. **一天一个文件。** 文件粒度即同步粒度，天然把双端冲突面压到最小。
3. **写入必须原子。** 先写临时文件再 rename，任何时刻断电都不产生半截文件。
4. **冲突绝不静默丢数据。** 程序不许替用户做删除决定。

## 目录布局

```
<日记根目录>/
└── YYYY/
    └── YYYY-MM-DD.md
```

示例：

```
diary/
├── 2025/
│   └── 2025-12-31.md
└── 2026/
    ├── 2026-01-01.md
    └── 2026-02-14.md
```

按年分目录，避免单个目录堆积上万个文件（Windows 资源管理器和 Syncthing 都会变慢）。

日记根目录由用户指定，默认 `我的文档/riji`。**同步工具同步的就是这个目录。**

## 文件格式

```markdown
---
id: 01JQX8K2M4P7R9T3V6W8Y0AB2C
date: 2026-02-14
created: 2026-02-14T08:12:33+08:00
updated: 2026-02-14T21:40:02+08:00
device: desktop-abc123
mood: 平静
tags:
  - 工作
  - 阅读
---

今天把日记程序的数据格式定下来了。

关键决定是**一天一个文件**，而不是全部塞进一个数据库。理由是可迁移性。
```

### Front matter 字段

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `id` | 是 | ULID (26 字符) | 条目永久标识。**必须是 ULID 而非自增整数**，否则两台设备各自新建会撞号 |
| `date` | 是 | `YYYY-MM-DD` | 日记归属日期，与文件名一致。允许补写往日日记 |
| `created` | 是 | ISO 8601 带时区 | 首次创建时刻 |
| `updated` | 是 | ISO 8601 带时区 | 最后修改时刻。同步冲突时的裁决依据 |
| `device` | 是 | 字符串 | 写入设备标识，用于排查同步问题、追溯来源 |
| `mood` | 否 | 字符串 | 心情。**自由文本**，不是枚举 |
| `weather` | 否 | 字符串 | 天气。**自由文本**，不是枚举 |
| `tags` | 否 | 字符串数组 | 标签 |
| `enc` | 否 | 字符串 | 加密格式版本（当前 `v1`）。出现即表示这天**锁着**，见下节 |
| `enc-params` | 否 | 字符串 | 口令派生参数，形如 `m=64MiB,t=3,p=1`。**跟着文件走**，所以文件是自描述的 |
| `enc-body` | 否 | 字符串 | 整天锁的密文。出现时正文必须是空的 |
| `enc-redactions` | 否 | 映射 | 按段锁的密文，键是 `r1`、`r2`……对应正文里黑条出现的顺序 |
| `chars` | 否 | 整数 | 锁上那一刻的**完整字数**。正文是密文或黑条时算不出来，但热力图要它 |

**`mood` 和 `weather` 刻意是自由文本而不是枚举。** 界面上给了预设值方便三秒钟点完，
但字段本身不限制取值：天气有"小雨转阴"、"闷热"、"雾霾"这类说法，
心情更是没法穷举。把它限定成固定选项，用户就会遇到"想写的东西写不下"。
代价是无法直接做严格的统计，需要统计时再做归并。

**时间一律带时区偏移**（如 `+08:00`）。不带时区的时间戳在跨设备场景下必然出歧义。

### 扩展字段与前向兼容（硬性要求）

**读取方必须能安全地「不认识」某些字段。**

新增字段（天气、位置、心情曲线……）时，只要遵守下面两条，就不会破坏任何已有数据：

1. **读取时**：不认识的 front matter 键必须**逐字节原样保留**，不得丢弃、不得重新序列化。
2. **写入时**：把保留的原文原样写回。

为什么这是硬性要求而不是"最好做到"：日记会在多台设备间同步，而各设备的程序版本
不可能永远一致。电脑端升级后写入了 `weather`，手机端还是旧版本——旧版本若在保存时
把 `weather` 抹掉，再同步回电脑端，这个字段就**无声地永久消失**了。
用户永远不会知道自己的数据少了一块。这正是本规范存在的意义。

对无法解析的前言块，程序同样不丢弃：原文会被注释化写回（每行加 `# `），
既留下痕迹，又让文件的元数据重新变得可读，而不是被永久毒化。

**加新字段的完整步骤：**

1. 在 `DiaryEntry` 上加字段；`DiaryCodec.decode` 里带兜底值读取，`encode` 里写出
2. **把键名加进 `DiaryCodec.knownFrontMatterKeys`**
3. 如果保存路径有"内容没变就不写盘"的优化，记得把新字段也加进比较条件
   （否则改了这个字段不会被写下去，而且无声无息）
4. 老版本**不需要任何改动**——它会自动把这批新字段原样保留

第 2 步是这套设计**唯一的陷阱**：漏了它，新字段既会被当成"不认识的字段"原样保留、
又会被模型自己写出一次，文件里就会出现两个同名键（`weather:` 出现两次）。
`diary_codec_test.dart` 里有测试专门守着这一条。

### 正文

正文是**原样保存的 Markdown**，程序不得擅自重排、转义或"美化"它。
用户手写的格式就是最终格式。

### 上锁的日记（`enc-*`）

锁着的内容**就在这个文件里**，不是搬到别处去了。两种形态：

**整天锁**——正文留空，整篇密文进 `enc-body`：

```
---
（…常规字段…）
chars: 2297
enc: v1
enc-params: m=64MiB,t=3,p=1
enc-body: "v1:Q2hhQ2hh…"
---

```

**按段锁（黑条）**——正文保留骨架，被锁的那一行变成 `████████`：

```
---
（…常规字段…）
enc: v1
enc-params: m=64MiB,t=3,p=1
enc-redactions:
  r1: "v1:Q2hhQ2hh…"
  r2: "v1:Q2hhQ2hh…"
---

今天去了医院复查。
████████
回来路上买了点菜。
```

**为什么密文放 front matter，而不是正文位置——这条是格式设计里最重要的：**

本规范第 77 行的前向兼容机制（未知键逐字节保留）在这里救了一次命。
以 v1.0.0 起的所有旧版本为例：它们不认识 `enc-*`，于是会把这些键原样收进
`extraFrontMatter` 并在保存时写回，正文位置看到的是空的——**旧版本打开这种
文件只会觉得"这天没正文"，动它也不会弄坏密文。**

反过来，如果把密文写在正文位置：旧版本里随手编辑一下，就会在密文后面追加
一行，GCM 校验随即失败，**那天的日记永久打不开**。这是不可接受的风险，
所以宁可 front matter 里有一行很长的 base64。

**读写硬性要求：**

1. `enc-body` 存在时正文**必须**是空的。正文非空 = 冲突，按既有纪律处理
   （另存冲突文件 + 明确提示），**两边都不许静默丢弃**。
2. 读取 `enc-params` 时必须校验并限制在合理区间（内存 8 MiB–512 MiB、
   迭代 1–16、并行 1–8）。越界一律视为**参数不可用**，而不是照着执行——
   一行 `m=4096MiB` 就能把内存撑爆。参数不可用时锁**仍然建立**（`params`
   为 null），界面据此说"参数不认识，打不开"，而不是显示成"这天没内容"。
3. 黑条行 = **整行去掉空白后全是 `█`（U+2588）且至少 2 个**。黑条旁边写了字
   （`██████ 后来说了`）就不再是黑条行，而是普通正文。
4. **黑条行数 > `enc-redactions` 条数时拒绝保存**。多出来的黑条底下没有密文，
   界面上看着"锁着"、其实正文一搜就搜得到——这是最坏的一种谎。
   反过来密文多出来（用户删掉了一行黑条）是允许的，多余的密文**保留不删**：
   程序不替用户销毁任何东西。
5. 黑条一律写成 8 个方块，**长度不代表原文长短**。
6. `chars` 在锁上那一刻写入。之后若在**已解锁**状态下编辑保存，会重新计算；
   未解锁时保持原值（那时算不出准确字数）。
7. 两种形态**互斥**（程序只会创建一种）。万一文件里两者都有，读取时两个都
   留着、整天密文优先显示，重新保存原样写回。

加密算法、密钥派生、保险库文件（`.vault`）和恢复码见
[`加密设计.md`](加密设计.md)。

## 原子写入协议

写一个条目的完整步骤：

1. 序列化为字符串，写入同目录下的临时文件 `.<name>.tmp-<随机后缀>`
2. `flush` + `fsync`（确保数据真正落盘，而非停在系统缓存）
3. `rename` 覆盖目标文件（同分区 rename 是原子操作）
4. 若第 3 步失败，删除临时文件并向上报错

**草稿保护：** 编辑器内容变化后防抖 1 秒写入 `<根目录>/.drafts/YYYY-MM-DD.draft`。
下次启动若发现草稿比正式文件新，提示用户恢复。日记程序最不可原谅的 bug 就是丢字。

## 同步策略

**不自建同步服务。** 二选一：

- **Syncthing** —— 实时、免费、无云、端到端加密。手机端用 Syncthing-Fork。
- **私有 git 仓库** —— 多一层版本历史和后悔药，适合定时 commit。

两者都必须忽略以下派生物：

```
.index.sqlite        # 搜索索引，可随时重建
.drafts/             # 本机草稿，不该跨设备传播
*.tmp-*              # 写入过程中的临时文件
```

### 冲突处理

同一天被两台设备同时编辑时：

1. 比较 `updated` 时间戳，较新者保留在 `YYYY-MM-DD.md`
2. 较旧者另存为 `YYYY-MM-DD.conflict-<timestamp>-<device>.md`
3. **通知用户手动合并**

绝不静默覆盖。宁可多一个需要手动处理的文件，也不能少一句用户写过的话。

## 搜索

数据量极小：一年 365 个文件，写十年也才 3650 个。
桌面端用 SQLite FTS5 建索引以求快速；**手机端可直接全量扫描 + 正则匹配**，
无需索引也能做到毫秒级响应。这就是"一天一文件"相对数据库方案的额外好处。

## 迁移与导出

- 导出功能**第一天就要有**，哪怕只是"打包 zip"。数据被锁死在程序里是最大的风险。
- 索引库版本号写在 `.index.sqlite` 的 `meta` 表中，版本不匹配时**直接删除重建**，
  不做就地升级——索引是可再生的，重建永远比迁移代码便宜。
