# 加密设计（方案 C：按天可选，只加密正文）

**状态：已确认，第一期实施中**（2026-10-08）。实现完这一份会被改写进 `详细说明.md`。

已确认的决定（2026-10-08）：

| # | 决定 |
|---|---|
| 1 | 黑条是**真加密**：文件里写 `██████`，原文加密后存 front matter；另有「抹掉」（不可逆）作为独立动作 |
| 2 | 第一期**只做按段**（整行变黑条）；句子中间任意片段放第二期 |
| 3 | 算法：**XChaCha20-Poly1305**（192 位 nonce，纯 Dart 下比软件 AES 更快）|
| 4 | 解锁粒度：**会话 + 按次都做**（按次只为一次搜索/一次查看解密，用完即丢）|
| 5 | **不填充**密文、**保留字数**在 front matter 里（热力图照旧）。这意味着"那天写了多少"是公开的，**这条要写在界面上** |

## 0. 先说清楚它防谁

| 场景 | 能不能防 |
|---|---|
| 笔记本丢了 / 硬盘被拆走 | ✅ |
| 同步到网盘，被云服务商或别人看到 | ✅ |
| 同一台电脑上的另一个 Windows 用户 | ✅（密钥绑定当前用户时）|
| 有人趁程序开着、且已经解锁来看 | ❌ |
| 木马 / 键盘记录 / 截图 | ❌ |
| **忘了口令** | ❌ 没有后门，数据永久打不开 |

**永久不做**：明文派生的搜索索引（盲索引 / 可搜索加密）。理由一句话——它不要密钥就能暴露"哪几天提到了同一个词"这种共现模式，而日记的话题高度集中；拿到口令的人还能拿候选词逐个确认。本地程序没必要付这个代价，**密钥就在你手上，直接解密搜**。

## 1. 数据格式（唯一不可逆的部分，先定这一条）

明文的那天：**和现在完全一样**，一个字节都不动。

锁上的那天：**front matter 里多几个字段，正文留空**。

```
---
date: 2026-10-08
mood: 平静
weather: 晴
tags:
  - 日常
chars: 412
enc: v1
enc-params: m=64MiB,t=3,p=1
enc-body: <base64，一行>
---

```

按段加锁（黑条）时，正文里那**一行**变成黑条，原文进 `enc-redactions`：

```
---
date: 2026-10-08
mood: 平静
chars: 412
enc: v1
enc-params: m=64MiB,t=3,p=1
enc-redactions:
  r1: <base64>
  r2: <base64>
---

今天去了医院复查。
████████
回来路上买了点菜。
```

「写几行黑条」和「哪几段是黑的」是**按出现顺序对应的**：第 1 行黑条取 `r1`，第 2 行取 `r2`。
黑条固定 8 个 `█`，长度**不代表**原文长短。

**为什么密文放在 front matter 字段里，而不是正文位置**——这是整份设计里最重要的一条：

- **所有已发布的旧版本都不会弄坏它。** 实测过 v1.0.0 / v1.2.0 / v1.3.0：不认识的 front matter 字段会被原样收进 `extraFrontMatter`，并在保存时写回。旧版本打开这种文件只会看到"这天没有正文"，**动它也不会破坏密文**。
- 反过来（密文当正文写）就有真实的数据损失风险：旧版本里随手编辑一下，会在密文后面追加一行 → GCM 校验失败 → **那天的日记永久打不开**。这条不能接受。

明文/密文混排的规则（新版本必须遵守）：

- `enc-body` 存在时正文必须是空的。**正文非空 = 冲突**，按既有纪律处理（另存冲突文件 + 明确提示），**两边都不许静默丢弃**。
- `enc` 是格式版本；将来换算法就是 `v2`，旧文件继续能读。
- 读取 `enc-params` 时必须校验并限制在合理区间——被改成 `m=1GiB` 要拒绝，不能让它撑爆内存。
- **黑条行数 > `enc-redactions` 条数时拒绝保存**（例子：有人手打了一行 `████████`）。多出来的密文（黑条被删掉了）**保留不删**。
- `chars` 只在这天有内容时写；锁着的天也照写（第 5 条决定的代价）。

⚠️ 这几条要写进 `docs/DATA-FORMAT.md`（那是全项目唯一不可逆的部分）。

## 1.5 一条关键的安全设计：编辑区里永远是"磁盘上的形式"

解锁之后**编辑区照旧显示黑条本身**，原文只在**只读浮窗**里看（点黑条 → 弹出原文 + 「复制」）。

为什么这样设计：如果解锁后把原文填回编辑框，保存时程序就必须知道"哪几段该重新加密"——
而用户可以在编辑框里任意增删改，行号会失效，一旦追踪错位就可能**把明文写回磁盘**（而且悄无声息）。
让编辑区始终等于磁盘形式，保存逻辑就**不需要任何新的追踪**，也不存在这条泄密路径。

于是解锁后能做的事：

| 动作 | 结果 |
|---|---|
| 搜索 | 包含锁着的正文 ✅ |
| 点黑条看原文 | 只读浮窗 ✅（不写回编辑框）|
| **锁上这一段** | 当前行原文加密 → 行变黑条，`enc-redactions` 多一条 ✅ |
| **解开这一段** | 这条黑条**变回明文**写进正文，密文从 front matter 删掉（明确提示：磁盘上从此是明文）✅ |
| 直接编辑黑条行之外的内容 | 照旧，不影响任何密文 ✅ |


## 2. 加密本身

| | |
|---|---|
| 算法 | **XChaCha20-Poly1305**（AEAD，192 位随机 nonce；纯 Dart 下比软件 AES 更快，也不依赖硬件指令）|
| 口令 → 密钥 | **Argon2id**，参数写进 `enc-params`（**文件自描述**：只把 `.md` 拷到另一台机器，有口令就能打开）|
| 主密钥 | **随机 32 字节**，不直接由口令派生。口令只用来**包裹**它（wrap），见第 2.5 节 |
| nonce | 每次加密随机 192 位，存在密文头里 |
| AAD | 日期（`YYYY-MM-DD`）+ 用途（`body` / `redaction`）+ 格式版本 → 防止把密文从这个文件挪到那个文件 |
| 库 | 纯 Dart（`cryptography` 包：`Xchacha20.poly1305Aead()` + `Argon2id`），**不引入任何插件**（项目的硬规矩）|

口令错和文件坏要分得开：密文头里放一小段**钥匙校验值**（用主密钥加密的固定串）。先验它——口令错就明确说口令错，逐文件解密失败才说那个文件坏了。不能一律报"打不开"。

## 2.5 保险库文件与恢复码

口令**不直接当密钥**。真实密钥是一个随机生成的主密钥，它有两份包裹：

```
<日记目录>/.vault            ← 跟着日记走，备份/同步都会带上它（没有它，备份就是一堆解不开的密文）
{
  "v": 1,
  "kdf": {"algo": "argon2id", "m": 65536, "t": 3, "p": 1, "salt": "<base32>"},
  "wrapped": "<用口令派生的密钥包裹后的主密钥>",
  "check":   "<钥匙校验值>"
}
```

- 用**口令**解锁 → Argon2id 派生 KEK → 解开 `wrapped` → 得到主密钥
- 用**恢复码**解锁 → 恢复码就是主密钥本身的 base32（分组显示）→ 直接用
- 恢复码**绝不落盘**（只在设置时显示一次，要求抄写并确认）

这样设计的好处：改口令只需重新包裹一次主密钥（不用重加密所有日记），而且"忘了口令还有恢复码"这条路是真的。


## 3. 解锁

三种粒度，共用同一个"解锁"动作，差别只是密钥留多久。**前两个都在第一期**：

| 粒度 | 行为 | 排期 |
|---|---|---|
| **会话**（默认） | 解锁一次，本次运行内所有功能都能用；有「锁定」按钮；退出自动锁 | ✅ 第一期 |
| **按次** | 只为这一次搜索（或这一次查看）解密，用完立即丢 | ✅ 第一期 |
| 本机记住 | 用 Windows DPAPI 把主密钥绑到当前用户，开机不用输（谁用你的账号谁就能看）| 第二期 |

**解锁 = 把锁着的那几天的正文解密进内存。** 这一步做完：

- **搜索一行都不用改**——它现在就是"纯内存全量扫描 + 纯逻辑判定"（`diary_controller.dart` 的 `_query` + `core/diary_filter.dart` 的 `matches()`）
- 时光机、每日一问、热力图、字数统计全部照旧
- 性能：解密只在解锁时发生一次，不是每次按键

**搜索结果不完整必须明说**（和"绝不静默覆盖"同一类纪律）。命中为 0 时那行提示也要显示：

```
┌─ 搜索日记 ───────────────────┐
│ 雨                            │
└───────────────────────────────┘
  2026-10-06  🔒  …那天下雨，我…
  ─────────────────────────────
  正文没有命中（另有 3 篇已锁，未参与搜索）
                        [ 输入口令一并搜索 ]
```

## 4. 哪些地方必须一起加密

方案 C 的波及面比预想小：**历史快照、回收站、备份存的都是"文件内容"**，源文件是密文，它们自然就是密文。

| 路径 | 要做什么 |
|---|---|
| `.history/` 快照 | 靠"落盘出口只有一个"这条纪律保证 ✅ |
| `.trash/` 回收站 | 同上（软删除 = 移动文件）✅ |
| 备份 | 同上（文件级复制）✅ |
| **`.drafts/` 草稿** | **要改**：编辑锁着的天时，草稿也必须加密落盘 |
| **导出 Markdown** | **要改**：导出前明确提示"这份是明文" |
| 每日提醒脚本 | 不用改：front matter 是明文，锁着的天照样算"写过" |

⚠️ **纪律：所有落盘都走同一个出口**（"entry → 字节"的那一个函数），由它按这天锁没锁决定写明文还是密文。只要存在第二条落盘路径，就一定会有明文漏出去——这是这个功能最容易翻车的地方，要有测试钉住。

## 7. 第一期不做（避免范围膨胀）

- 全库加密（方案 B 的效果）——之后可以加，复用同一套机制
- **句子中间任意片段的黑条**（第二期；要处理"用户把黑条删掉一半"这类问题）
- 改口令（`wrapped` 已经为此留好了路，但界面留到第二期）
- 闲置自动锁定、本机记住（DPAPI）
- 密文填充到固定长度（第 5 条决定：不填充，保留字数）
- 手机端解密（手机本来就没这个程序）
- 盲索引（永久不做）

## 程序锁（进入程序时的口令）

### 防什么、不防什么

| | |
|---|---|
| **防** | 别人用你**已登录的电脑**点开这个程序 |
| **不防** | 绕过程序直接去翻 `.md` 文件的人 —— 没有加密的日子在磁盘上仍然是明文 |

所以程序锁是**栅栏**，不是保险柜；真正的保护始终是「日记加密」。
第一次打开开关时会弹一次说明，之后不再弹（设置项 `appLockNoticeShown`）。

### 行为

- 打开程序先看到锁屏，**不渲染任何日记内容**（列表、正文、搜索结果一个都不构建）
- 口令和日记加密**共用同一个**，不再多一个密码让人记
- **锁定 = 丢密钥 + 清空内存里的日记**。只丢密钥是不够的：明文的日子本来就以明文读进了内存，
  那样"锁上"只是屏幕上看不见
- 清空之前先 `_flush()`：锁定绝不能吃掉还没落盘的编辑
- 解锁之后 `reloadAfterUnlock()` 把内容读回来
- `lockApp()` 里的清空逻辑是**反向验证**过的：把那几行拆掉，`diary_controller_test` 会变红

### 什么时候会锁

- 闲置 N 分钟（1/5/10/15/30 可选，默认 10；1 分钟那档是为了方验证）
- `Ctrl+L`、命令面板「立即锁定」、底栏「已解锁」、加密对话框里的「立即锁定」
- 这几个入口**行为一致**：开了程序锁就一律走 `lockApp()`（清内存 + 回锁屏）
- **刻意不做"窗口失焦就锁"**：切出去查个东西就被锁在外面，这功能最后只会被关掉

### 一个刻意的例外

保险库文件读不出来时，锁屏上直接给一个「直接进入」的口子 ——
**绝不能把人锁在自己的日记外面。**

### 与「解锁来搜索」的关系

开了程序锁之后，进程序时就已经输过口令，所以「解锁来搜索」这条路碰不到（设计如此）。
它服务于"没开程序锁、只锁了会话"的场景：那时左侧会显示「另有 N 篇已加密」+「解锁来搜索」。
